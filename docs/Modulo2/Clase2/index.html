VetCare · Módulo 2 · Clase 2

El token deja de estar guardado y empieza a proteger

Conecta el JWT con cada petición, bloquea rutas privadas antes de mostrar la pantalla y exige autenticación real en el backend.

Angular Spring Security JWT VetCare
🚨
01 · Punto de partida

Admin autenticado, petición rechazada

La sesión existe en Angular, pero el backend nunca recibe la credencial.

Decide antes de revelar

Si cien peticiones necesitan el mismo JWT, ¿debería cada servicio escribir el header por su cuenta?

Piensa en qué ocurriría cuando aparezca el servicio número once o cambie el lugar donde vive el token.

Ver respuesta

No. La autenticación transversal necesita un único punto de control.

Repetir el header funciona hasta que un servicio lo olvida. Un interceptor aplica la misma política a todas las peticiones y permite cambiarla en un solo lugar.

Estado heredado

VetCare ya tiene login, registro, AuthService, un JWT en localStorage y autorización por rol en operaciones de dueños.

El token todavía no viaja, las rutas de Angular siguen abiertas y el backend mantiene mascotas y dueños con permitAll().

🛡️
02 · Modelo mental

Dos guardias, dos responsabilidades

Proteger una pantalla no equivale a proteger los datos que viajan hacia la API.

📨 Interceptor HTTP

Revisa cada petición de HttpClient, adjunta el JWT solo al backend propio y observa respuestas como 401.

🚪 Guard de rutas

Decide si Angular puede activar una pantalla. Sin sesión, devuelve una redirección a /login.

🏦 Spring Security

Es la barrera real. Aunque alguien evite la interfaz y llame la API directamente, el backend exige autenticación.

i

La idea que organiza la clase

El interceptor protege el viaje, el guard cuida la experiencia de navegación y el backend impone la seguridad. Ninguno sustituye a los otros.

📨
03 · Concepto central

El interceptor trabaja en la cadena HTTP

Una función recibe la petición, decide si la clona y continúa la cadena con next.

Qué es y por qué existe

HttpInterceptorFn describe una función que procesa solicitudes antes de enviarlas y respuestas cuando regresan.

Las peticiones de Angular son inmutables: para cambiar headers se crea una copia con req.clone().

Detecta el riesgo · 30 segundos

¿Qué ocurriría si el JWT se adjuntara a cualquier URL, incluidas imágenes de servidores externos?

Comprobar razonamiento

Respuesta: la aplicación enviaría una credencial privada a terceros. El interceptor debe comprobar que la URL pertenece al backend de VetCare antes de agregar el header.

Modificarsrc/app/services/auth.service.ts
import { Injectable, signal, computed, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Router } from '@angular/router';

export interface Credenciales {
  username: string;
  password: string;
}

interface NuevoUsuario {
  username: string;
  password: string;
  rol: 'USER' | 'ADMIN';
}

interface RespuestaAuth {
  token: string;
}

const CLAVE_TOKEN = 'vetcare_token';

@Injectable({
  providedIn: 'root'
})
export class AuthService {
  private http = inject(HttpClient);
  private router = inject(Router);
  private apiUrl = 'http://localhost:8080/api/auth';

  private tokenSignal = signal<string | null>(
    localStorage.getItem(CLAVE_TOKEN)
  );
  private errorSignal = signal<string | null>(null);

  sesionActiva = computed(() => this.tokenSignal() !== null);
  token = this.tokenSignal.asReadonly();
  error = this.errorSignal.asReadonly();

  iniciarSesion(credenciales: Credenciales) {
    this.errorSignal.set(null);

    this.http.post<RespuestaAuth>(
      `${this.apiUrl}/login`,
      credenciales
    ).subscribe({
      next: (respuesta) => {
        this.tokenSignal.set(respuesta.token);
        localStorage.setItem(CLAVE_TOKEN, respuesta.token);
        this.router.navigateByUrl('/');
      },
      error: () => {
        this.errorSignal.set('Usuario o contraseña incorrectos.');
      }
    });
  }

  registrar(credenciales: Credenciales) {
    this.errorSignal.set(null);

    const nuevoUsuario: NuevoUsuario = {
      ...credenciales,
      rol: 'USER'
    };

    this.http.post<RespuestaAuth>(
      `${this.apiUrl}/registro`,
      nuevoUsuario
    ).subscribe({
      next: (respuesta) => {
        this.tokenSignal.set(respuesta.token);
        localStorage.setItem(CLAVE_TOKEN, respuesta.token);
        this.router.navigateByUrl('/');
      },
      error: () => {
        this.errorSignal.set(
          'No se pudo registrar. ¿Ese usuario ya existe?'
        );
      }
    });
  }

  cerrarSesion(redireccion: '/' | '/login' = '/') {
    this.tokenSignal.set(null);
    localStorage.removeItem(CLAVE_TOKEN);
    this.router.navigateByUrl(redireccion);
  }
}

05 · Construcción activa

Adjuntar el JWT sin filtrarlo a terceros

El interceptor evalúa destino, sesión y tipo de endpoint antes de cambiar la petición.

Predice · 45 segundos

¿Debería un 401 del endpoint de login cerrar la sesión y redirigir, o mostrar “credenciales incorrectas” en el formulario?

Comprobar decisión

Respuesta: el login debe manejar su propio 401. El cierre automático solo aplica cuando ya existe un token y falla una petición protegida.

01

Definir el límite de confianza

La barra final hace que http://localhost:8080.ejemplo.com no coincida por accidente. Los endpoints públicos de autenticación tampoco reciben un token existente.

Checkpoint

Antes de continuar

Las imágenes externas no reciben el JWT, login y registro conservan sus propios errores, y una sesión inválida termina en /login.

Ver jwt.interceptor.ts completoCrear · src/app/interceptors/jwt.interceptor.ts · TypeScript · listo para copiar
Crearsrc/app/interceptors/jwt.interceptor.ts
import {
  HttpErrorResponse,
  HttpInterceptorFn
} from '@angular/common/http';
import { inject } from '@angular/core';
import { catchError, throwError } from 'rxjs';
import { AuthService } from '../services/auth.service';

const URL_BASE_BACKEND = 'http://localhost:8080/';
const RUTA_AUTENTICACION = `${URL_BASE_BACKEND}api/auth/`;

export const jwtInterceptor: HttpInterceptorFn = (req, next) => {
  const authService = inject(AuthService);
  const token = authService.token();
  const esPeticionAlBackend = req.url.startsWith(URL_BASE_BACKEND);
  const esPeticionDeAutenticacion =
    req.url.startsWith(RUTA_AUTENTICACION);

  const debeAdjuntarToken =
    token && esPeticionAlBackend && !esPeticionDeAutenticacion;

  const peticion = debeAdjuntarToken
    ? req.clone({
        setHeaders: {
          Authorization: `Bearer ${token}`
        }
      })
    : req;

  return next(peticion).pipe(
    catchError((error: HttpErrorResponse) => {
      const sesionRechazada =
        error.status === 401 &&
        Boolean(token) &&
        esPeticionAlBackend &&
        !esPeticionDeAutenticacion;

      if (sesionRechazada) {
        authService.cerrarSesion('/login');
      }

      return throwError(() => error);
    })
  );
};

Qué aporta el tipo

HttpInterceptorFn verifica en compilación que la función respete el contrato. Angular la ejecuta porque se registra con withInterceptors(), no por la anotación de tipo por sí sola.

07 · Segundo concepto central

El guard decide antes de activar la ruta

La redirección se devuelve como resultado; no se dispara como efecto lateral.

Compara · 30 segundos

¿Qué comunica mejor la decisión: navegar a /login y luego devolver false, o devolver un UrlTree?

Ver criterio

Respuesta: devolver un UrlTree. Angular recibe una única decisión declarativa: reemplazar la navegación solicitada por la ruta de login.

Resultado posible

true permite activar la ruta. Un UrlTree redirige. Angular recomienda devolver la redirección en vez de retornar false y navegar manualmente.

Ver auth.guard.ts completoCrear · src/app/guards/auth.guard.ts · TypeScript · listo para copiar
Crearsrc/app/guards/auth.guard.ts
import { inject } from '@angular/core';
import { CanActivateFn, Router } from '@angular/router';
import { AuthService } from '../services/auth.service';

export const authGuard: CanActivateFn = () => {
  const authService = inject(AuthService);
  const router = inject(Router);

  return authService.sesionActiva()
    ? true
    : router.createUrlTree(['/login']);
};
!

Qué no garantiza este guard

sesionActiva() confirma que existe un token, no que siga vigente ni que su firma sea válida. Esa verificación pertenece al backend; un 401 posterior limpia la sesión.

09 · Seguridad real

El frontend no puede ser la única barrera

Cualquiera puede omitir Angular y llamar la API desde Swagger, Postman u otro cliente.

Para pensar

Si el guard ya bloquea la pantalla, ¿por qué cambiar también SecurityConfig?

Ver respuesta

Porque una ruta del navegador no protege un endpoint.

El guard mejora la experiencia. La autorización real ocurre en Spring Security, donde cada cliente —incluido uno que nunca carga Angular— debe presentar un token válido.

01

Eliminar las excepciones públicas

Al quitar los permitAll() de mascotas y dueños, esas rutas caen bajo anyRequest().authenticated(). Login, registro y documentación siguen públicos.

Ver securityFilterChain completoReemplazar método · src/main/java/.../config/SecurityConfig.java · Java · conservar package, imports y resto de la clase
Reemplazar métodosrc/main/java/.../config/SecurityConfig.java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http)
        throws Exception {
    http
            .cors(cors -> cors.configurationSource(
                    corsConfigurationSource()))
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/api/auth/**").permitAll()
                    .requestMatchers(
                            "/swagger-ui/**",
                            "/swagger-ui.html",
                            "/v3/api-docs/**"
                    ).permitAll()
                    .anyRequest().authenticated()
            )
            .sessionManagement(session -> session
                    .sessionCreationPolicy(
                            SessionCreationPolicy.STATELESS))
            .authenticationProvider(authenticationProvider())
            .addFilterBefore(
                    jwtFilter,
                    UsernamePasswordAuthenticationFilter.class);

    return http.build();
}
i

Autenticación no es autorización por rol

Un usuario USER autenticado puede consultar mascotas y dueños. Las operaciones con @PreAuthorize("hasRole('ADMIN')") siguen reservadas para ADMIN.

11 · Verificación observable

Seis pruebas, seis señales claras

No basta con que compile: cada responsabilidad debe demostrar su comportamiento.

  • Sin sesión: abrir /mascotas redirige de inmediato a /login.
  • Con sesión: /mascotas y /duenos cargan con normalidad.
  • Header real: Red → petición a la API → Authorization: Bearer ....
  • 401: alterar el token, pedir un recurso protegido y comprobar que se borra la sesión y aparece Login.
  • 403: un usuario USER intenta crear un dueño; conserva la sesión porque el token sí es válido.
  • API directa: Swagger sin Authorize recibe 401 al consultar mascotas.
Interpreta el resultado

Si Angular deja entrar a la pantalla, pero la primera consulta devuelve 401, ¿qué sabe el guard y qué sabe el backend?

Ver respuesta

Respuesta: el guard solo sabe que hay un valor almacenado. El backend sabe si su firma y vencimiento son válidos; por eso tiene la última palabra.

12 · Diagnóstico

Leer el síntoma antes de tocar el código

El código HTTP y el momento del fallo indican qué responsabilidad revisar.

No aparece el header

El interceptor compila, pero no está dentro de withInterceptors([...]). Angular nunca lo ejecuta.

401 Unauthorized

No existe una autenticación válida: token ausente, alterado o vencido. La sesión local debe limpiarse.

403 Forbidden

La identidad sí fue reconocida, pero el rol no permite la operación. No se debe cerrar la sesión.

Bucle en Login

/login fue protegido por accidente. El guard solo pertenece a rutas privadas.

!

Login fallido no equivale a sesión vencida

Un 401 en /api/auth/login debe alimentar el mensaje del formulario. Por eso el interceptor excluye los endpoints de autenticación de su cierre global.

14 · Cierre

VetCare ya distingue guardar una sesión de hacerla cumplir

El proyecto pasó de tener un token inerte a coordinar identidad, navegación y autorización.

  • Problema resuelto: el JWT ahora viaja sin repetir lógica en cada servicio.
  • Cambio visible: una persona sin sesión no entra a mascotas ni dueños.
  • Seguridad real: la API exige autenticación incluso fuera de Angular.
  • Idea 1: un interceptor centraliza políticas transversales de HTTP.
  • Idea 2: un guard organiza navegación; no reemplaza la seguridad del backend.
  • Idea 3: 401 y 403 describen problemas diferentes y exigen respuestas diferentes.
Puente a la siguiente clase

Si el JWT ya contiene el rol, ¿cómo podría Angular ocultar “Crear dueño” para un usuario que no sea ADMIN?

Guardar para la próxima sesión

Angular tendrá que leer el payload y convertir el rol en estado reactivo.

La siguiente necesidad ya no es “¿hay sesión?”, sino “¿qué puede hacer esta sesión?”.
