01 · VetCare

Recuento de la Clase 1

Angular, componentes, entradas y control de flujo: la base que hoy se convierte en navegación.

Situación de partida

"Antes de arrancar con lo nuevo, hagamos memoria. La clase pasada tocamos muchísimo por primera vez. Vamos a recordar el qué y el por qué, no solo el código."

Recuento 1 — ¿Dónde estamos parados en el curso?

Venimos de construir todo el backend de VetCare en Java (Spring Boot, JWT, base de datos). Ese backend ya existe y expone datos por una API.

Ahora estamos del otro lado del cable: el frontend, lo que el usuario ve y toca en el navegador. La herramienta para eso es Angular.

Recuento 2 — ¿Qué es Angular? (pregunta al grupo)

Para pensar

En una frase, ¿qué es Angular y para qué lo usamos?

Ver respuesta

Angular es un framework de Google para construir la interfaz de aplicaciones web, escrito en TypeScript. Es, para el frontend, lo que Spring Boot fue para el backend: organiza el código en piezas, tiene inyección de dependencias y trae un CLI (ng) para generar el esqueleto.

Una primera intuición habitual sería: Es como para hacer páginas web" o "es el frontend".

Recuento 3 — La pieza central: el componente

Un componente es un pedazo de pantalla reutilizable: un botón, una tarjeta, una tabla. Cada componente son tres cosas juntas:

1

HTML — la estructura (lo que se ve)

2

CSS — el estilo (cómo se ve)

3

TypeScript — la lógica (cómo se comporta)

Analogía: un componente es un ladrillo LEGO. Autónomo, con su forma, y armas cosas grandes combinando ladrillos pequeños.

Recuento 4 — Lo que construimos la clase pasada

Creamos el proyecto VetCare y una tarjeta de mascota (mascota-card). Esa tarjeta recibe datos de afuera con @Input y la mostramos varias veces con @for.

Este es el mascota-card.ts tal como quedó. se puede revisar así:

Estado inicialsrc/app/components/mascota-card/mascota-card.ts
import { Component, Input } from '@angular/core';

@Component({
  selector: 'app-mascota-card',
  templateUrl: './mascota-card.html',
  styleUrl: './mascota-card.css'
})
export class MascotaCard {
  @Input() nombre = '';
  @Input() especie = '';
  @Input() edad = 0;
}

Recuento 5 — Qué hace @Input (concepto que hoy reutilizamos)

@Input() marca una propiedad como una entrada: un dato que el componente recibe desde afuera.

Analogía: es como los parámetros de un método en Java. El componente no sabe qué mascota mostrará; se lo pasan cuando lo usan. Eso lo hace reutilizable. Guarden bien esta idea: hoy la vamos a reutilizar para leer datos que vienen en la URL.

Recuento 6 — Cómo se veía el catálogo

En app.ts teníamos la lista de mascotas, y en app.html la recorríamos con @for. Este era el app.html de cierre de la Clase 1:

Estado inicialsrc/app/app.html
<h1>Catálogo de {{ nombreClinica }}</h1>

@for (m of mascotas; track m.nombre) {
  <app-mascota-card
    [nombre]="m.nombre"
    [especie]="m.especie"
    [edad]="m.edad">
  </app-mascota-card>
}

Recuento 7 — Las sintaxis clave, una línea cada una

  • {{ dato }} → interpolación: muestra un dato en el HTML.
  • [propiedad]="valor" → property binding: le pasa un dato a un @Input.
  • @for (x of lista; track x.id) { ... } → repite un bloque por cada elemento.
  • @if (condicion) { ... } → muestra un bloque solo si la condición se cumple.

Con esto ya estamos alineados. Ahora sí, lo nuevo.

Arrancar y observar

El navegador queda abierto para comprobar cada cambio mediante recarga en caliente.

Por qué arrancamos ya

Antes de tocar código, vamos a encender la app y verla en el navegador. Así, cada cambio que hagamos hoy lo veremos reflejado al instante. Trabajar viendo el resultado es mucho más claro que construir a ciegas.

Paso 1 — Abrir el proyecto de la Clase 1

Abrimos VS Code y, dentro, la carpeta del proyecto VetCare que creamos la clase pasada. En VS Code: menú Archivo → Abrir carpeta → seleccionamos la carpeta vetcare.

Debe verse, en el panel izquierdo, la estructura del proyecto: una carpeta src, un package.json, etc.

Paso 2 — Abrir la terminal integrada

En VS Code abrimos la terminal integrada (la que usamos la clase pasada para instalar todo). Menú Terminal → Nueva terminal. Se abre abajo, ya parada en la carpeta del proyecto.

i

Recordatorio: la terminal integrada es la misma consola de siempre, pero adentro de VS Code, ya ubicada en el proyecto. No hay que navegar a ninguna carpeta.

Paso 3 — Levantar la aplicación

En esa terminal escribimos:

Terminalvetcare/
ng serve -o

Qué hace: compila la app, la sirve en http://localhost:4200 y abre el navegador solo (eso es el -o). Qué esperas ver: se abre una pestaña del navegador con el contenido de la Clase 1 (el catálogo de mascotas).

Dato clave que deben interiorizar hoy

ng serve se queda corriendo todo el tiempo. Cada vez que guardas un archivo (Ctrl+S), la app se recarga sola en el navegador. Eso se llama recarga en caliente. Regla de la clase: guardar y mirar el navegador después de cada cambio. No hay que reiniciar nada.

i

Si en algún momento quieres detenerlo: Ctrl + C en la terminal. Para volver a arrancar: ng serve otra vez.

03 · VetCare

La necesidad de más pantallas

Una situación de negocio revela por qué mostrar y ocultar todo en app.html no escala.

Situación de partida

"Tenemos el catálogo funcionando: una pantalla con todas las mascotas. Ahora la clínica VetCare me pide algo muy normal en cualquier app real."

Para pensar

El usuario ve la lista y hace clic en Firulais porque quiere ver su ficha completa: dueño, edad, próxima cita. ¿Cómo lo llevo a otra pantalla con solo la información de Firulais, sin recargar toda la aplicación?

Ver respuesta

En una aplicación Angular no hay muchas páginas HTML: hay una sola que se reescribe sola. Para "cambiar de pantalla" usamos el Router de Angular: cambia lo que se ve según la URL, sin recargar la página. Eso es lo que vamos a construir hoy, y lo vamos a dejar bonito.

Una primera intuición habitual sería: Abro otra página HTML" o "hago otro archivo y lo enlazo con un link normal.

El problema, dicho claro

Una app veterinaria real tiene muchas vistas: inicio, listado de mascotas, detalle de cada una, y más adelante citas, dueños, login. Meter todo eso en un solo app.html sería un archivo gigante, imposible de mantener, y rompe todo lo que enseñamos de componentes.

Para pensar

¿Y si metemos inicio, listado y detalle todos en el mismo app.html, mostrando y ocultando pedazos con @if según un botón?

Ver respuesta

Funciona al principio, pero se vuelve inmantenible: un archivo enorme, sin URLs propias, sin poder compartir el enlace directo de una mascota, sin botón "atrás" del navegador. La solución profesional es darle a cada vista su propia URL y dejar que el Router decida qué mostrar.

Una primera intuición habitual sería: Funcionaría, mostramos y escondemos con @if.

04 · VetCare

SPA y routing

Una sola página física, múltiples vistas y URLs que conservan el historial del navegador.

Definición técnica — SPA

SPA = Single Page Application (aplicación de una sola página). La app carga un solo index.html y, a partir de ahí, JavaScript reescribe el contenido según lo que el usuario hace. Nunca recarga la página completa.

Explicación sencilla

El navegador carga la app una vez. Cuando cambias de "pantalla", no se pide una página nueva al servidor: Angular borra lo que hay y dibuja lo siguiente en el mismo lugar. Por eso se siente instantáneo.

Aplicación en la vida real

Gmail, Spotify web, Netflix: haces clic y la vista cambia al instante, sin el parpadeo blanco de recargar. Eso es una SPA. VetCare va a funcionar igual.

Definición técnica — Routing

Routing es el mecanismo que decide qué componente se muestra según la URL actual.

  • URL /mascotas → muestra el listado.
  • URL /mascotas/1 → muestra el detalle de la mascota con id 1.

Conexión con el backend que ya conocen

En el backend, @GetMapping("/mascotas/{id}") mapeaba una URL a un método del controller. El routing de Angular es la misma idea, del lado del frontend: mapea una URL a un componente. No es un concepto nuevo; es el patrón que ya dominan, del otro lado del cable.

05 · VetCare

El router como recepcionista

Un modelo mental para entender URL, tabla de rutas, componentes y outlet.

La analogía

Imagina la recepción de VetCare. Llega alguien y dice a dónde quiere ir ("quiero ver el listado de mascotas"). La recepcionista (el Router) mira la petición y lo manda al consultorio correcto (el componente).

  • La URL es lo que pide el visitante.
  • La tabla de rutas es la lista de consultorios que la recepcionista conoce.
  • El componente es el consultorio donde termina.

Las piezas que vamos a construir hoy (y en qué orden)

1

Primero, las páginas (Inicio, Listado, Detalle) — los consultorios.

2

Luego, el cascarón con la barra de navegación y el <router-outlet> — la recepción.

3

Después, la tabla de rutas en app.routes.ts — la lista de consultorios.

4

Al final, mejoras: parámetros y lazy loading.

Vamos en ese orden a propósito: construimos las piezas primero, y al final las conectamos y vemos todo funcionando junto.

06 · VetCare

Sistema de diseño

La identidad de VetCare se define una vez y se reutiliza en todas las vistas.

Por qué el diseño va primero, no al final

En el front, el diseño no es maquillaje que se pone al terminar. Si defino primero mis colores y espaciados, cada pantalla que construya después ya nace coherente. Al revés (estilar cada pantalla suelta, sin sistema) se produce una app donde cada vista se ve distinta. Eso se ve amateur.

Qué es un "sistema de diseño"

Definición técnica

Un conjunto de decisiones visuales reutilizables: paleta de color, espaciado, tipografía, sombras. Se definen una vez y se usan en todo el producto.

Explicación sencilla

Es como el manual de marca de una empresa: el mismo azul, la misma letra, los mismos márgenes en todos lados. Da sensación de "producto serio".

Dato para el grupo

Spotify, Airbnb, cualquier banco tienen su sistema de diseño documentado. Nosotros haremos una versión mínima para VetCare.

La herramienta: variables CSS

En vez de escribir el azul a mano en 30 lugares, lo definimos una vez como variable y lo reutilizamos. El día que el cliente diga "cámbiame el azul", se cambia en un solo lugar y toda la app se actualiza. Eso es mantenibilidad real.

Paso 1 — Abrir el archivo de estilos globales

Abrimos el archivo src/styles.css.

i

Ojo: es styles.css (plural, con "s"), el que está directamente dentro de src/, no dentro de ninguna carpeta de componente. Este archivo ya existe desde que se creó el proyecto; hoy es la primera vez que lo tocamos. Es el único CSS que afecta a toda la app.

Al abrirlo, probablemente esté vacío o casi vacío. Está bien.

Paso 2 — Escribir el sistema de diseño

Borramos lo que haya y pegamos esto en src/styles.css:

Comprobación

Checkpoint ·

Miramos el navegador. La app ya cambió de fondo: pasó de blanco puro a un azul clarísimo. Todavía se ve simple, pero ya respira la nueva identidad. Ese cambio de fondo es la señal de que el archivo global está funcionando.

Qué significa cada parte

  • :root { --variable: valor } → aquí se declaran las variables. :root significa "toda la app". Cada --nombre es una variable que luego usamos con var(--nombre).
  • Colores como variables → un solo lugar de la verdad. Cambiar la marca es cambiar una línea.
  • Espaciado en múltiplos de 8 → todos los márgenes salen de la misma escala. Eso es lo que hace que una interfaz se vea "ordenada"; el ojo percibe el ritmo aunque no sepa por qué.
  • box-sizing: border-box → hace que el padding no agrande las cajas de forma inesperada. Es el primer ajuste que pone cualquier front profesional.

Criterio UX que vale nombrar en voz alta

El fondo no es blanco puro, es azul clarísimo. Las tarjetas, más adelante, serán blancas. Ese pequeño contraste hará que las tarjetas "floten" sobre el fondo. Es un truco de jerarquía visual: el usuario distingue capas sin que se lo digan.

Iterar también es diseñar

En la Clase 1 la tarjeta salió en verde. Hoy migramos a azul y lo dejamos como paleta oficial de VetCare. Si preguntan por el verde: iterar el diseño es normal, los productos reales ajustan su identidad. Lo importante es que desde hoy todo es coherente.

07 · VetCare

Página de Inicio

Primer componente-página, un llamado a la acción y navegación interna sin recarga.

Antes de crear: ¿qué es una "página" y en qué se diferencia de una "pieza"?

Hasta ahora tenemos una pieza: mascota-card, un ladrillo pequeño y reutilizable. Hoy creamos páginas: pantallas completas a las que se llega por una URL (Inicio, Listado, Detalle).

Para ordenarlas, las vamos a poner en una carpeta llamada pages. Buena noticia: no tenemos que crear la carpeta a mano. El CLI de Angular la crea sola cuando generamos el primer componente dentro de ella. Ahora lo verán.

Paso 1 — Generar el componente de Inicio con el CLI

En la terminal integrada de VS Code (la misma donde corre ng serve, pero necesitamos una libre) escribimos:

Terminalvetcare/
ng generate component pages/inicio
i

Si ng serve está ocupando la terminal, abrimos una segunda terminal: en VS Code, el ícono + arriba a la derecha del panel de terminal. Así una queda sirviendo la app y en la otra escribimos comandos.

Qué acaba de pasar (importante mirarlo juntos)

Al ejecutar ese comando, Angular:

1

crea la carpeta src/app/pages/inicio/ (y la carpeta pages porque no existía);

2

adentro crea cuatro archivos: inicio.ts, inicio.html, inicio.css, inicio.spec.ts.

En la terminal aparecen varias líneas que empiezan con CREATE. Eso confirma que salió bien. En el panel izquierdo de VS Code, ahora aparece la carpeta pages con inicio dentro. Que la vean aparecer es parte del aprendizaje.

Por qué usamos el CLI y no creamos los archivos a mano

Crear los cuatro archivos a mano es lento y propenso a errores (un nombre mal escrito y no funciona). El CLI los crea bien conectados entre sí y ya deja el componente standalone por defecto. Es la misma idea de Spring Initializr en el backend: generar el esqueleto correcto sin escribirlo letra por letra.

Paso 2 — Abrir inicio.ts y ver qué generó el CLI

Abrimos src/app/pages/inicio/inicio.ts. El CLI lo dejó más o menos así (los nombres pueden variar ligeramente según la versión):

Revisar generadosrc/app/pages/inicio/inicio.ts
import { Component } from '@angular/core';

@Component({
  selector: 'app-inicio',
  imports: [],
  templateUrl: './inicio.html',
  styleUrl: './inicio.css'
})
export class Inicio {}

Esto ya funciona. Solo le vamos a agregar una cosa: la capacidad de tener enlaces de navegación.

Paso 3 — Preparar inicio.ts para navegar

El HTML de Inicio va a tener un botón que lleva al listado. Para que un enlace navegue en Angular, el componente necesita importar RouterLink.

Dejamos src/app/pages/inicio/inicio.ts así:

Reemplazarsrc/app/pages/inicio/inicio.ts
import { Component } from '@angular/core';
import { RouterLink } from '@angular/router';

@Component({
  selector: 'app-inicio',
  imports: [RouterLink],
  templateUrl: './inicio.html',
  styleUrl: './inicio.css'
})
export class Inicio {}

Guardamos.

La regla de oro de standalone (repetir hoy varias veces)

Un componente standalone declara en su propio imports todo lo que su HTML usa. Si la plantilla usa routerLink, hay que importar RouterLink. Este es el error #1 de principiantes en Angular: usar algo en el HTML sin haberlo importado en el imports. Hoy lo van a ver varias veces; cada vez lo señalamos.

Paso 4 — Escribir el HTML de Inicio

Abrimos src/app/pages/inicio/inicio.html. El CLI dejó adentro un texto de ejemplo (algo como "inicio works!"). Borramos todo y escribimos:

Reemplazarsrc/app/pages/inicio/inicio.html
<section class="hero">
  <h1 class="hero-titulo">Bienvenido a VetCare</h1>
  <p class="hero-texto">
    El sistema para gestionar las mascotas y su atención en la clínica.
  </p>
  <a routerLink="/mascotas" class="boton">Ver mascotas</a>
</section>

Guardamos.

Qué es la línea routerLink="/mascotas"

Es un enlace interno de Angular. A diferencia de un <a href> normal (que recarga toda la página), routerLink le pide al Router que cambie de vista sin recargar. Lo probaremos en el Bloque 11, cuando las rutas estén encendidas. Por ahora solo lo dejamos escrito.

Criterio UX del Inicio

Una pantalla de inicio necesita un solo llamado a la acción principal (aquí: "Ver mascotas"). Cuando hay un botón claro y evidente, el usuario sabe qué hacer sin pensar. Llenar el inicio de diez botones iguales dispersa la atención. Menos es más.

i

Nota: todavía no veremos el Inicio en el navegador, porque aún no hemos creado las rutas que le dicen a Angular "cuando la URL sea /, muestra Inicio". Eso pasa en el Bloque 11. Es normal; estamos construyendo las piezas primero.

Qué carga criterio en este CSS

  • var(--azul-principal), var(--espacio-md) → aquí usamos las variables que definimos en el Bloque 6. El Inicio ya nace con la identidad del sistema. Cero colores sueltos escritos a mano.
  • max-width: 640px + margin: 0 auto → limita el ancho del texto y lo centra. Un texto que cruza toda la pantalla cansa la vista; acotar el ancho es una regla básica de legibilidad.
  • transition + :hover → el botón cambia de color suavemente al pasar el mouse. Ese feedback le dice al usuario "esto es clickeable". Es UX básico: la interfaz responde.
08 · VetCare

Página de Listado

Datos, fotos, grilla responsiva y enlaces dinámicos para cada mascota.

Qué vamos a hacer aquí

La lista de mascotas que hoy vive en app.ts la vamos a mudar a su propia página, el Listado. Y de paso le agregamos a cada mascota dos datos nuevos: un id (que necesitaremos para el detalle) y una foto (una tarjeta sin foto se ve incompleta).

Paso 1 — Generar el componente de Listado

En la terminal:

Terminalvetcare/
ng generate component pages/mascotas-listado

Qué esperas ver: otra vez las líneas CREATE, ahora en src/app/pages/mascotas-listado/. En el panel izquierdo aparece la nueva carpeta mascotas-listado junto a inicio.

Paso 2 — Escribir la lógica del Listado (con id y foto)

Abrimos src/app/pages/mascotas-listado/mascotas-listado.ts. Reemplazamos todo su contenido por esto:

Reemplazarsrc/app/pages/mascotas-listado/mascotas-listado.ts
import { Component } from '@angular/core';
import { RouterLink } from '@angular/router';
import { MascotaCard } from '../../components/mascota-card/mascota-card';

@Component({
  selector: 'app-mascotas-listado',
  imports: [RouterLink, MascotaCard],
  templateUrl: './mascotas-listado.html',
  styleUrl: './mascotas-listado.css'
})
export class MascotasListado {
  mascotas = [
    { id: 1, nombre: 'Firulais', especie: 'Perro', edad: 4, foto: 'https://placedog.net/400/300?id=1' },
    { id: 2, nombre: 'Michi', especie: 'Gato', edad: 2, foto: 'https://loremflickr.com/400/300/cat?lock=2' },
    { id: 3, nombre: 'Rocky', especie: 'Perro', edad: 6, foto: 'https://placedog.net/400/300?id=7' }
  ];
}

Guardamos.

Leyendo este archivo con calma

  • import { MascotaCard } from '../../components/...' → traemos la tarjeta que ya construimos en la Clase 1. Los ../../ significan "sube dos carpetas" (de pages/mascotas-listado/ hasta app/) para llegar a components/.
  • imports: [RouterLink, MascotaCard] → declaramos lo que el HTML va a usar: enlaces (RouterLink) y la tarjeta (MascotaCard). Si falta uno, no funciona.
  • La lista mascotas → es la misma de la Clase 1, pero con dos campos nuevos por mascota: id y foto.

De dónde salen las fotos (explicarlo, es la duda del grupo)

La foto es simplemente una URL de una imagen en internet. Usamos servicios gratuitos que devuelven fotos de mascotas sin registrarse ni descargar nada:

  • https://placedog.net/400/300?id=1 → una foto de perro de 400×300 píxeles. El ?id=1 fija cuál perro, para que sea siempre el mismo y no cambie en cada recarga.
  • https://loremflickr.com/400/300/cat?lock=2 → una foto de gato de 400×300. El lock=2 cumple lo mismo: fija la imagen.

No se crea ninguna carpeta ni se descarga ningún archivo. La imagen vive en internet y el navegador la trae por su URL, igual que cualquier foto de una página web. En una app real, esta URL vendría del backend (la foto que subió el dueño de la mascota). Hoy la escribimos a mano, como el resto de los datos.

Aviso honesto para la clase en vivo

Como las fotos vienen de internet, necesitan conexión. Si un día el servicio va lento o una imagen no carga, no es un error del código: es la red. Cuando eso pasa, en lugar de la foto se muestra un texto (el alt, que pondremos en el Bloque 9). La clase sigue sin problema.

Detalle y parámetros

El id de la URL llega como entrada, se convierte y permite manejar casos inexistentes.

Volvemos a la pregunta del inicio de la clase

El usuario hace clic en Firulais. La URL ya cambia a /mascotas/1 (lo armamos en el Listado). En este momento, si hacen clic en una tarjeta, el <router-outlet> muestra el Detalle vacío (el que generó el CLI). Falta que ese Detalle lea el 1 de la URL y muestre a Firulais.

La pregunta que abre el tema

Para pensar

El componente Detalle es uno solo, pero debe servir para Firulais, Michi, Rocky y cualquier mascota futura. ¿Cómo sabe ese componente cuál mascota mostrar?

Ver respuesta

No le pasamos la mascota: le pasamos su id, que viene en la URL. El componente lee el id y con él busca los datos. Hoy busca en una lista local; en la Clase 4 usará ese mismo id para pedirle al backend GET /mascotas/1. Y la forma moderna de leer ese id reutiliza algo que ya conocen: @Input.

Una primera intuición habitual sería: Le pasamos la mascota completa, como a la tarjeta.

La conexión que hace todo elegante

En la Clase 1, @Input recibía datos de un componente padre. Angular permite que @Input también reciba el parámetro :id de la URL, conectándolo a un @Input() id. Solo hay que activar esa conexión una vez, en la configuración. Empecemos por ahí.

Paso 1 — Activar el binding de parámetros a inputs

Abrimos src/app/app.config.ts (el que solo miramos antes). Le agregamos withComponentInputBinding() dentro de provideRouter:

Reemplazarsrc/app/app.config.ts
import { ApplicationConfig } from '@angular/core';
import { provideRouter, withComponentInputBinding } from '@angular/router';
import { routes } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes, withComponentInputBinding())
  ]
};

Guardamos.

Observa dos cambios: agregamos withComponentInputBinding al import de arriba, y lo llamamos como segundo argumento de provideRouter.

Qué hace withComponentInputBinding

Le dice al Router: "cuando una ruta tenga un parámetro (:id), pásalo automáticamente al @Input que se llame igual en el componente." Es la pieza que conecta la URL con un @Input. Sin ella, el @Input() id del Detalle llegaría vacío.

La forma antigua de hacer esto era inyectar un servicio (ActivatedRoute) y suscribirse manualmente: más código y más conceptos nuevos. Esta forma es la moderna y la más limpia, y reutiliza el @Input que ya dominan.

Abrimos src/app/pages/mascota-detalle/mascota-detalle.ts. Reemplazamos todo su contenido por esto:

import { RouterLink } from '@angular/router';

@Component({
  selector: 'app-mascota-detalle',
  imports: [RouterLink],
  templateUrl: './mascota-detalle.html',
  styleUrl: './mascota-detalle.css'
})
export class MascotaDetalle {
  @Input() id = '';

  private mascotas = [
    { id: 1, nombre: 'Firulais', especie: 'Perro', edad: 4, dueno: 'Ana Torres', foto: 'https://placedog.net/600/400?id=1' },
    { id: 2, nombre: 'Michi', especie: 'Gato', edad: 2, dueno: 'Luis Pérez', foto: 'https://loremflickr.com/600/400/cat?lock=2' },
    { id: 3, nombre: 'Rocky', especie: 'Perro', edad: 6, dueno: 'María Gómez', foto: 'https://placedog.net/600/400?id=7' }
  ];

  get mascota() {
    return this.mascotas.find(m => m.id === Number(this.id));
  }
}

Guardamos.

Leyendo las tres piezas clave

  • @Input() id = '' → recibe el id que viene en la URL, gracias a withComponentInputBinding. Es el mismo @Input de siempre, pero ahora el dato llega de la ruta, no de un padre.
  • private mascotas = [...] → por hoy, el Detalle tiene su propia lista (con un dato extra: dueno, y fotos más grandes). En la Clase 3 quitaremos esta duplicación con un servicio.
  • get mascota() → un getter: una función que se usa como si fuera una propiedad. Busca en la lista la mascota cuyo id coincide con el de la URL y la devuelve.

El error silencioso #1

Miren esta parte: m.id === Number(this.id).

Todo lo que viene en una URL es texto: /mascotas/1 trae el string "1", no el número 1. Pero los id de la lista son números (1, 2, 3). Comparar "1" === 1 en TypeScript da falso. Por eso convertimos con Number(this.id).

Este es el bug más común aquí: sin el Number(...), el detalle "no encuentra" ninguna mascota y nadie entiende por qué. Que lo sepan de antemano les ahorra media hora de frustración.

Lazy loading

Cada página se descarga cuando se visita y el comportamiento se verifica en Network.

El problema que todavía no se ve, pero existe

Ahora mismo, al abrir la app, todo el código de las tres páginas se descarga de una, aunque el usuario solo quiera ver el Inicio. Con tres páginas no se nota. Pero una veterinaria real tendría citas, dueños, reportes, facturación... cuarenta pantallas. Descargarlas todas de golpe haría que la app abra lenta.

La pregunta de negocio

Para pensar

Si un usuario entra solo a ver el Inicio y nunca abre reportes ni facturación, ¿tiene sentido que su navegador descargue el código de reportes y facturación apenas abre la app?

Ver respuesta

No tiene sentido, y no tiene que ser así. Con lazy loading (carga perezosa), el código de cada página se descarga solo cuando el usuario visita esa ruta. La app abre más rápido porque al inicio baja solo lo mínimo. Es el estándar profesional en apps que crecen.

Una primera intuición habitual sería: No, pero así viene por defecto, ¿no?

Definición y analogía

Definición técnica

Lazy loading es cargar un recurso en el momento en que se necesita, no antes. En routing: el código de una página se descarga al navegar a su ruta, no al arrancar la app.

Analogía de la vida real

Un buffet no te sirve todos los platos apenas entras. Te sirve el plato que pides, cuando lo pides. Lazy loading es igual: el navegador trae cada página cuando el usuario la pide, no todas de golpe.

Paso 1 — Convertir las rutas a lazy loading

Abrimos src/app/app.routes.ts (el que ya escribimos en el Bloque 11). Lo reemplazamos completo por esta versión:

Reemplazar · versión finalsrc/app/app.routes.ts
import { Routes } from '@angular/router';

export const routes: Routes = [
  {
    path: '',
    loadComponent: () =>
      import('./pages/inicio/inicio').then(m => m.Inicio)
  },
  {
    path: 'mascotas',
    loadComponent: () =>
      import('./pages/mascotas-listado/mascotas-listado').then(m => m.MascotasListado)
  },
  {
    path: 'mascotas/:id',
    loadComponent: () =>
      import('./pages/mascota-detalle/mascota-detalle').then(m => m.MascotaDetalle)
  }
];

Guardamos.

Esta es la versión final de app.routes.ts.

Dos cosas cambiaron — mirémoslas juntas

1. Desaparecieron los import de arriba. Antes, al inicio del archivo, importábamos cada página (import { Inicio } from ...). Con lazy loading esos imports de arriba se quitan. Si los dejáramos, la página se cargaría de una y perderíamos el beneficio.

2. component: se volvió loadComponent:.

  • component: Inicio → "muestra este componente" (ya cargado).
  • loadComponent: () => import(...) → "cuando visiten esta ruta, entonces ve a buscar este componente".

Leyendo una ruta lazy línea por línea

  • loadComponent: () => ... → una función que el Router llama solo cuando se visita la ruta.
  • import('./pages/inicio/inicio') → descarga ese archivo en ese momento (esto es un import dinámico).
  • .then(m => m.Inicio) → cuando termina de descargar, toma la clase Inicio de ese archivo.

Eso que acaban de ver es lazy loading: el código llega bajo demanda, no todo de entrada. Verlo en vivo vale más que mil explicaciones.

Cuándo NO usar lazy loading (criterio)

Si una página se necesita siempre y de inmediato (por ejemplo, un encabezado presente en todas las pantallas), cargarla perezosamente no aporta. Lazy loading brilla en páginas que no todos visitan: reportes, administración, configuración. Es criterio, no una receta para aplicar a ciegas.

IA con criterio

Un prompt preciso y una lista de validación para evitar patrones antiguos de Angular.

Cómo integro la IA hoy

La IA es rápida generando rutas, componentes y estilos. Pero genera con frecuencia sintaxis vieja de Angular: *ngIf, RouterModule.forRoot, ActivatedRoute con suscripciones. Eso es exactamente lo que no usamos.

Un buen prompt para hoy

Este prompt especifica la versión y el patrón moderno:

"Genera las rutas de una app Angular 22 standalone con provideRouter, usando loadComponent para lazy loading y withComponentInputBinding para leer parámetros de ruta como @Input. Sin NgModule, sin RouterModule."

Ser específico con la versión y las funciones evita que devuelva el patrón antiguo.

Qué validar en la respuesta de la IA

Para pensar

La IA te devuelve un detalle que lee el id con ActivatedRoute y .subscribe(...). ¿Lo aceptas porque funciona?

Ver respuesta

Funciona, pero no es lo que enseñamos ni lo más limpio. Nosotros leemos el id con @Input + withComponentInputBinding: menos código, y reutiliza lo que ya saben. Aceptar código solo porque "funciona", sin criterio de si es la forma actual y mantenible, es lo que separa a un junior de un senior.

Una primera intuición habitual sería: Sí, si funciona da igual.

Errores que la IA suele meter aquí

  • Usa ngIf / ngFor en vez de @if / @for.
  • Propone un app.module.ts con @NgModule (patrón viejo, ya no lo usamos).
  • Convierte el id sin Number(...) y el find nunca coincide.
  • En CSS, mete colores sueltos en vez de reutilizar tus variables.

Revisar el código antes de aceptarlo es la disciplina de la clase, no un detalle.
