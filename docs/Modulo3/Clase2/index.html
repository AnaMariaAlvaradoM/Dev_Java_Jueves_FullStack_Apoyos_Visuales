Concepto central 1: calidad es evidencia

Por qué empezamos aquí y no en el código

El backend de Colmena ya trae las ocho reglas de una reserva desde la Clase 1. No las vamos a programar: las vamos a demostrar. Y para demostrar algo, primero hay que escribir qué se espera.

3.1 · Qué es una prueba

Definición técnica

Una prueba (test) es la ejecución controlada de una parte del sistema con datos conocidos, para comparar el resultado que se obtiene con el resultado que se esperaba.

Explicación sencilla

Es como probar la llave antes de entregarle la oficina a un cliente: sabes qué debería pasar (la puerta abre) y compruebas si pasa.

Aplicación profesional

En Colmena, una prueba es: "Laura reserva la Sala Panal mañana de 9:00 a 11:00 con 4 personas → espero 201 y un valor de $ 90.000". Si responde otra cosa, encontramos un error antes que Mariana.

3.2 · Caso de prueba, caso límite y resultado esperado

Caso de prueba

Técnica: una combinación concreta de entrada, persona y estado del sistema, con su resultado esperado.

En la vida real: la receta de un chequeo: "con este carné, en esta puerta, a esta hora, debe abrir".

Caso límite

Técnica: el valor que queda justo en el borde de una regla: el último que se permite o el primero que no.

En la vida real: el pasajero que llega cuando la puerta del avión se está cerrando. Ahí es donde se equivocan las reglas.

En Colmena: la Sala Polen admite 4 personas. El caso límite es 4 (se permite) y 5 (no se permite). Si el programador escribió >= donde iba >, solo el caso límite lo descubre.

Resultado esperado

Técnica: el código HTTP y el mensaje que deberían salir, escritos antes de ejecutar la prueba.

Por qué antes: si lo escribes después de ver la respuesta, terminas justificando lo que salió. Escribirlo antes es lo que convierte "probé" en "demostré".

3.3 · La matriz de pruebas

Definición técnica

Una matriz de pruebas es una tabla donde cada fila es un caso de prueba y las columnas dicen qué regla cubre, como quién se prueba, con qué datos, qué se espera y qué se obtuvo.

Explicación sencilla

Es la lista de chequeo del piloto antes de despegar: no confía en la memoria, sigue la lista.

Por qué nos importa en Colmena

Mariana no quiere "confíe en nosotros". Una matriz con 14 filas y todas en verde es la demostración que pidió.

400 (Bad Request) significa que los datos no tienen sentido, sin importar el estado del sistema: 9:15 nunca es un bloque válido. 409 (Conflict) significa que los datos están bien, pero chocan con el estado actual: 16:00 a 17:00 es un horario válido, pero hoy ya está tomado.

Concepto central 2: la prueba automática

Lo que resuelve

Una prueba automática repite filas de la matriz en segundos, siempre igual, cada vez que alguien corre un comando.

5.1 · Qué es una prueba automática de endpoint

Definición técnica

Es un programa que levanta la aplicación, le envía peticiones HTTP como lo haría un cliente (Angular, Swagger, Postman) y compara cada respuesta con la esperada. Si alguna no coincide, la prueba falla y dice cuál y por qué.

Explicación sencilla

Es un cliente incansable que hace las mismas preguntas cada vez y anota si la respuesta cambió. No se cansa, no se le olvida una fila y no "cree" que funciona.

Aplicación profesional

En los equipos reales, nadie sube un cambio sin que las pruebas pasen. En tu taller pasa exactamente esto: cada git push corre pruebas como la que vamos a leer, y de ahí sale tu nota.

Las tres piezas que intervienen

Pieza Qué es Para qué está aquí
JUnit La librería de pruebas de Java Corre cada método marcado con @Test y reporta cuál pasó y cuál falló
Spring Boot Test La integración de Spring con JUnit Levanta Colmena completa (controladores, seguridad, base de datos) dentro de la prueba
H2 Una base de datos que vive en la memoria La prueba no toca colmena_db: cada vez arranca vacía, se siembra y se borra al terminar

6.1 · Qué es validar en dos capas

Definición técnica

Es aplicar las mismas reglas en dos lugares con propósitos distintos: en el cliente (Angular), para dar retroalimentación inmediata antes de enviar; y en el servidor (Spring), como la decisión final que nadie puede saltarse.

Explicación sencilla

Es como el formulario del banco y el cajero. El formulario impreso te dice "escriba la cédula aquí, 10 dígitos": te ayuda a no equivocarte. Pero el que revisa de verdad es el cajero. Si alguien llena mal el formulario a propósito, el cajero lo rechaza igual.

Aplicación profesional

En Colmena, si Laura escoge 9 personas para la Sala Panal, el formulario le avisa al instante, sin llamar al backend. Si de todas formas la petición llega (porque alguien usó Swagger), el backend responde 400 con el mismo mensaje.

  private apiUrl = `${API_URL}/espacios`;

  error = this.errorSignal.asReadonly();

        this.lista.set(datos);
        this.cargandoSignal.set(false);
      },
      error: (error: HttpErrorResponse) => {
        this.errorSignal.set(mensajeDeError(error));
        this.cargandoSignal.set(false);
      }
    });
  }

        this.lista.update(actuales =>

        );
      },
      error: (error: HttpErrorResponse) => this.errorSignal.set(mensajeDeError(error))
    });
  }

Las tres ideas de hoy

  1. Calidad es evidencia: casos normales, límites y errores, con el resultado esperado escrito antes de probar.
  2. Una prueba automática repite la evidencia: se lee como una frase, se corre con un comando y, cuando falla, dice qué, dónde y por qué.
  3. Validar en dos capas: el formulario orienta antes de enviar; el backend protege y su mensaje se muestra tal cual.

La decisión técnica importante

Las reglas del formulario están en validaciones.ts, separadas de la página y con los mismos mensajes del backend. Así se pueden reutilizar en otra pantalla, se pueden probar sin Angular y, cuando cambie una regla, se sabe exactamente dónde cambiarla (y que hay que cambiarla también en el backend).
